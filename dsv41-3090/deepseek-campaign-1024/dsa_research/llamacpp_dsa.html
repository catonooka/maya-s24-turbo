Recently I submitted PR #21149 that adds support for DeepseekV32ForCausalLM with lightning indexer and DeepSeek Sparse Attention (DSA) implementation. I'd like to have it properly tested to confirm that the implementation works correctly and can serve as a reference for further optimizations.

Some background: in DeepSeek V3.2 (and related) DSA attention works exactly like MLA up to 2048 tokens, then they may start slightly diverge. So benchmarks with short/moderate length questions and answers are not good for this. What we need are very long reasoning chains where a slight mistake is fatal for the final answer or maybe some other long-context tests.

My initial idea is to use lineage-bench with very large number of lineage graph nodes (at least 512). I already used lineage-bench to test DeepSeek V3.2 Speciale in sglang with both dense (MLA) and sparse (DSA) attention up to lineage-1024, results are here:

If we can reproduce this result (whole or limited subset) with llama.cpp this is convincing enough for me. But running this requires a lot of VRAM (at least 8x RTX PRO 6000 for Q8_0) and may take a long time. So if anyone has a better idea let me know.

During my work on the implementation I did some lineage-128 tests with DeepSeek V3.2 Exp model (20 quizzes due to limited compute). I found that the model underperformed (accuracy around 70%) compared to OpenRouter benchmark run (accuracy 90%). This allowed to me to find a bug in Hadamard transform implementation, after fixing it accuracy in the limited local benchmark run went up to 95%. This is may be anecdotal evidence, but it's a data point confirming that lineage-bench is well suited for detecting subtle flaws in the implementation.

Detailed steps for reproducing the benchmark results:

Environment

I confirmed that the implementation works without problems with CUDA 13.2 and CCCL 13.2.27. Earlier versions of CUDA currently have problems with ggml_top_k() implementation.

I rebased PR, so fix for ggml_top_k() is already present. CCCL is no longer needed, CUDA should work even for 12.X versions.

Downloading the model

uvx hf auth login
uvx hf download "sszymczyk/DeepSeek-V3.2-Speciale-light-GGUF" --include="Q8_0/*"
uvx hf download "sszymczyk/DeepSeek-V3.2-Speciale-light-GGUF" --include="Q4_K_M/*"

Building llama.cpp

git clone https://github.com/fairydreaming/llama.cpp -b deepseek-dsa --single-branch
cd llama.cpp
uv pip install nvidia-cuda-cccl
mkdir build
cd build
cmake .. -DGGML_CUDA=ON -DGGML_CUDA_USE_CUB=ON
make -j16

Starting llama-server

./bin/llama-server -m /workspace/.hf_home/hub/models--sszymczyk--DeepSeek-V3.2-Speciale-light-GGUF/snapshots/d8151a1c295b0bd7f9ee10e7d88d2b36baaf5257/Q4_K_M/DeepSeek-V3.2-Speciale-light-Q4_K_M-00001-of-00031.gguf --no-warmup --mmap --host 127.0.0.1 --port 6666 --jinja --chat-template-file ../models/templates/deepseek-ai-DeepSeek-V3.2.jinja -c $((128*1024)) -np 1 -ub 512 -fit off -ngl 99

Exact context size and the number of parallel sequences to be set later.

Installing lineage-bench

git clone https://github.com/fairydreaming/lineage-bench
cd lineage-bench
uv venv
source .venv/bin/activate
uv pip install -r requirements.txt
mkdir results

Running lineage-bench

Full benchmark run:

for length in 8 128 256 512 1024; do ./lineage_bench.py -s -l $length -n 25 -r 42|./run_openrouter.py --url http://127.0.0.1:6666/v1/chat/completions -t 1 -m "deepseek-ai/DeepSeek-V3.2-Speciale" -r --temp 1.0 --top-p 0.95 --max-tokens $((128*1024)) -o "results/DeepSeek-V3.2-Speciale_DSA_$length"|tee "results/DeepSeek-V3.2-Speciale_DSA_$length.csv"; done|./compute_metrics.py

Limited lineage-512 benchmark run:

for length in 512; do ./lineage_bench.py -s -l $length -n 25 -r 42|./run_openrouter.py --url http://127.0.0.1:6666/v1/chat/completions -t 1 -m "deepseek-ai/DeepSeek-V3.2-Speciale" -r --temp 1.0 --top-p 0.95 --max-tokens $((128*1024)) -o "results/DeepSeek-V3.2-Speciale_DSA_$length"|tee "results/DeepSeek-V3.2-Speciale_DSA_$length.csv"; done|./compute_metrics.py

cc @AesSedai who volunteered his hardware for the benchmark runs.

@AesSedai I rented 8x RTX PRO 6000S instance and did some experiments to see what llama-server parameters would be best. Since we don't care much about prompt processing (prompts are short in lineage-bench, from few hundred tokens for lineage-8 up to a few thousands tokens for lineage-1024) I think the best approach is to lower ubatch size so that the model compute buffer is small (but prompt processing rate will suck) and this way we can fit larger context for more concurrent sequences.

I included rough estimates of how much time lineage-512 run would take with -n 25 (100 quizzes). These numbers look very bad. I guess Q8_0 is out of the question and we should go either with Q4_K_M with 32 parallel requests in case we want to do 100 quizzes or with 8 parallel requests in case we want to do only 40 quizzes (that's the absolute minimum I'd like to do, I think it would take ~13 hours).

Let me know how much compute time you are willing to spend on this. Don't worry about power consumption, from what I saw in nvidia-smi all GPUs used below 150W even for 32 parallel requests, so it shouldn't be a problem. There may be higher spikes during prompt processing, though. I suppose it's best to start small and see if results are worth continuing.
